# Experimental Setup

## Model Roles and Inference Configuration

The implementation separates final multimodal answer generation from retrieval control. The answer model receives the location-prefixed question, the available benchmark images, and, when retrieval succeeds, textual evidence returned by the retrieval agent. The controller model selects and invokes retrieval, confidence, query-enrichment, keyword-extraction, and web-ingestion tools according to the active configuration. The driver exposes the answer and controller checkpoints separately, although both roles may point to the same served model. Crop enrichment and keyword extraction also use the controller endpoint.

The repository does not establish a Qwen-3 subject-model run. Its checked-in generation launcher selects `meta-llama/Llama-3.2-11B-Vision-Instruct`, while the only Qwen-3 implementation evidence is an evaluation client whose default model label is `Qwen3-32B` and whose maximum completion length is 10,000 tokens. A historical log names `Qwen/Qwen3-32B` as a judge but records no successful identification judgments in the displayed run; it therefore establishes neither the judge used for the present study nor a completed Qwen-3 evaluation. We do not infer any subject-model or final-judge assignment from these artifacts. As implementation defaults, the local answer client requests at most 4,096 completion tokens with temperature 0.8 and nucleus parameter $p=0.95$. The controller does not set sampling parameters in the driver, whereas crop enrichment uses temperature 0 and a 1,024-token output limit. Valid input images are transmitted separately by default. An optional preprocessing mode combines at most three images into a labeled panel whose cells are $512\times512$ pixels. Missing image paths are omitted. These are available code paths rather than verified settings of the reported study; the selected image mode, validated image count per record, sampling parameters, seeds, and number of independent runs must be recorded in the run manifest.

The distinction between declared and wired factors is essential. `MainAgent` reads and applies the five agent-level switches shown as wired, using them to gate tool registration and select a matching controller instruction. Each experimental row consequently requires a validated launch manifest that binds the named agent configuration to the three driver-level controls, the runtime-collection mode, and a unique output path. No checked-in wrapper currently provides a validated execution of every row. The intended comparisons can be interpreted as effects of configuration access only after the launch bindings and manipulation checks described below are verified. In particular, the two static candidates would isolate access to crop enrichment, the static and progressive candidates without crop enrichment would isolate progressive filtering, and the two full-system candidates would isolate access to location-aware domain filtering. Web-enabled comparisons additionally require versioned search responses or a common search protocol, because live results can change independently of the configured domain filter. Freshness between conditions does not make examples independent within a web-enabled condition. All retrieval workers in one run share the same mutable runtime collection. Evidence ingested for one benchmark example can therefore be retrieved for a later example, and concurrent completion order can determine which evidence is visible at a given request. The driver permits two in-flight retrieval requests per detected GPU, making this order potentially nondeterministic. If this accumulating memory is part of the evaluated online protocol, dispatch and completion order, ingestion events, and the final runtime snapshot must be preserved. ## Benchmark and Evaluation Cohort

The available standard MIRAGE benchmark contains 8,188 agricultural question-answer records. Each record includes an expert answer, one to three images, a category, entity annotations, county and state labels, and an asked-time field. The three identification categories contain 4,324 records: 2,600 plant-identification, 1,146 insect- or pest-identification, and 578 plant-disease-identification examples. The four management and guidance categories contain 3,864 records: 1,611 plant-care and gardening-guidance, 1,049 plant-disease-management, 725 insect- or pest-management, and 479 weeds- or invasive-plant-management examples. The expert answer and entity annotations are used by evaluation and are not supplied to inference.

The file contains 8,184 unique identifier strings because four identifiers each label two rows with distinct image filenames. The experimental cohort must therefore assign a collision-free row identifier or apply a documented deduplication rule before inference. The resulting ordered identifier list and benchmark hash must be frozen across conditions. Evaluation must use the same paired set for every condition rather than silently dropping rows without completed answers. Every intended record should receive a terminal status, and the protocol must predefine the treatment of hard retrieval failures, soft retrieval fallback, generation failures, missing images, and invalid judge outputs. [DETAIL REQUIRES VERIFICATION: benchmark variant and hash, geographic or category filters, duplicate rule, validated image-path counts, final identification and management counts, and failure or exclusion policy.]

## Retrieval and Corpus Configuration

The runtime defaults to `BAAI/bge-base-en-v1.5`, producing normalized 768-dimensional query vectors for cosine search in Qdrant. Query text is truncated to 512 embedding-model tokens. The retrieval tool defaults to at most five returned chunks, although its `k` parameter is exposed to agent calls and is not enforced as an experiment-wide constant by the driver. The executed value must therefore be captured in tool traces or fixed at the interface.

Progressive retrieval evaluates the combinations that can be formed from a location-derived hardiness zone and any `month_year` or title supplied in the controller's tool call, together with semantic-only retrieval. The benchmark asked-time field is not passed to the retrieval tool and must not be described as the source of `month_year`. Conditions without progressive filtering evaluate semantic retrieval alone. Each enabled collection selects its best strategy independently using the mean of $1/(2-s)$ over returned cosine similarities $s$. The base and runtime candidates are then merged, content-deduplicated, globally ranked by raw similarity, and truncated to the requested budget. The strategy label passed to confidence scoring is taken from the collection that returned the larger candidate list; it is not selected through a global comparison of both collections' strategy scores.

The curated collection is expected under the name `mirage_base`, while web-acquired evidence is written to an ablation-scoped runtime collection. The repository contains code for building `mirage_base_build`, but it does not contain a completed corpus manifest or the procedure that promotes or restores that collection as `mirage_base`. It also uses different explicit embedding-normalization settings in the preload notebook and runtime embedder. [DETAIL REQUIRES VERIFICATION: curated snapshot name and cryptographic hash, point/chunk/document counts, state and source coverage, build date, inclusion rules, embedding checkpoint revision, Qdrant server version, promotion or restore procedure, and vector equivalence across preload and runtime ingestion.]

Web-enabled configurations query the You.com search service. When suitable location-linked domains exist, domain filtering restricts the search to at most six land-grant or university domains derived from the record's state and hardiness zone. Retrieved pages are cleaned and, when longer than 512 embedding-model tokens, divided into 480-token chunks with an 80-token overlap. Chunks are deduplicated against the enabled collections before insertion into the runtime store. Search-result `month_year` is derived first from the provider's `page_age` field and then, if available, from an explicit provider `month_year` value. If neither yields a valid value, the client substitutes the machine's current month at search time. This fallback is ingestion metadata rather than verified publication metadata.

The domain-filter comparison requires either a versioned search-response cache or complete request and response artifacts for both conditions. The record should include queries, provider parameters, timestamps, result ordering, returned URLs, page-content hashes, fetch failures, and ingestion-success counts. [DETAIL REQUIRES VERIFICATION: search interval, caching policy, provider configuration, retry behavior, and retained web artifacts.]

## Inference Environment and Failure Handling

The driver communicates with model servers through an OpenAI-compatible interface and with Qdrant through its HTTP client. It starts one retrieval worker per visible GPU and assigns retrieval workers to consecutive endpoints beginning at port 11434. Final-generation processes, by contrast, all use the single endpoint supplied through `--openai_api_base`. This asymmetry affects contention and must be preserved in a reproduction. A checked-in Slurm example requests three H200 GPUs, 125 GB of memory, and eight CPU cores and launches three Llama-based SGLang endpoints; it is an available example, not evidence of the Qwen-3 experimental environment. [DETAIL REQUIRES VERIFICATION: executed hardware, endpoint topology, serving commands, process counts, scheduler allocation, and wall-clock limits.]

Final generation makes up to five attempts per record with a five-second interval and writes `-1` plus an error string after exhausting them. A retrieval-agent error containing an infrastructure keyword triggers at most one retry. The current worker pairs exceptions with no agent text; after the retry, that missing text satisfies the driver's soft-failure predicate, so the item is recorded as `soft_fail` and generation continues from the effective query without retrieved text. The nominal `hard_fail` branch would require a hard-classified error paired with at least 30 characters of agent text, a combination the current worker does not emit. Non-infrastructure errors, missing responses, and shorter terminal text enter the same soft fallback without an infrastructure retry. The direct-generation path uses the location-prefixed question and images without starting retrieval workers or crop enrichment. These statuses must be retained and reconciled against the frozen cohort before scoring.

The repository supplies a dependency snapshot containing, among other packages, PyTorch 2.9.1, Transformers 4.57.1, SentenceTransformers 5.2.0, SGLang 0.5.7, Qdrant Client 1.18.0, Google ADK 1.21.0, LiteLLM 1.80.0, and OpenAI Python 2.6.1. These pins describe an available candidate environment. They become the experimental environment only after the executed Python, operating-system, CUDA, GPU-driver, and Qdrant-server versions and the lockfile hash are captured from the jobs.

## Evaluation Protocol

Evaluation separates the three identification categories from the four management and guidance categories. For identification, the judge receives the question, expert answer, annotated entity names, and model response. It returns binary identification accuracy and a reasoning score from 0 to 4 based on observable clues, descriptive precision, and causal coherence. The reporting script expresses mean identification accuracy as a percentage and mean reasoning accuracy on its original 0--4 scale.

For management and guidance, the judge returns four scores from 0 to 4: factual accuracy, relevance, completeness, and parsimony. The reporting script first rounds each dimension's sample mean to two decimals and then computes

\[
S_{\mathrm{MG}} = \frac{2A + R + C + P}{20},
\]

where $A$, $R$, $C$, and $P$ are the rounded means. Accuracy thus receives twice the weight of each other dimension, and the composite lies in $[0,1]$ for valid scores.

The current judge scripts make at most five attempts. On the local-model path, they accept a parsed JSON object when the expected keys are present, without enforcing integer type or rubric range. After five exceptions, they append `"score": -1`; end-of-job cleanup subsequently removes rows whose score is `-1` or null, so those benchmark items are absent rather than assigned a terminal evaluation outcome. An interrupted job can retain the uncleaned sentinel, and a keyed dictionary with invalid value types or ranges can survive cleanup. Both cases are unsafe for the reporting script, which assumes a valid score dictionary. The evaluation used for reported results must validate both schema and allowed range, retain raw judge output, assign an explicit terminal status after exhausted retries, and apply the same predefined invalid-output policy to all conditions. ## Logging, Manipulation Checks, and Reproducibility

Inference appends per-record JSONL entries containing the answer or failure value, chat history when generation succeeds, retrieval endpoint and attempt, a coarse web-search flag, and retrieval status and use flags. Complete tool sequences, selected retrieval strategies, chunk identities, confidence values, enriched queries, URLs, and ingestion outcomes are currently transient rather than structured output fields. After successful completion, the runtime manager optionally creates a snapshot and then deletes the live runtime collection; interrupted runs preserve the live collection.

Each reported condition should therefore retain a machine-readable launch manifest and an augmented trace. The manifest should bind the code revision, benchmark hash and ordered row IDs, configuration ID, driver-level controls, model and embedding revisions, prompt hashes, base-snapshot hash, runtime-memory policy, image mode, sampling and seed settings, hardware, endpoints, concurrency, software versions, and timestamps. Web-enabled manifests should identify the search-response cache or retained live-search artifacts. Snapshotting or an equivalent export is required when adaptive evidence is part of the reproducibility record.

Manipulation checks should report crop-enrichment attempts, changed queries, and failures; retrieval and confidence calls; selected strategies and retrieved chunk IDs; low-confidence frequency; web calls and returned URLs; successful page ingestions; second-retrieval compliance; evidence passed to generation; and soft, hard, generation, and judge failures. Until these traces establish actual invocation, comparisons measure access to the configured capabilities rather than guaranteed execution of each component.
