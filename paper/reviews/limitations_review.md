# Limitations Review

## Overall assessment

The section is substantively strong and unusually careful about separating the implemented system from calibrated uncertainty, real-world agronomic diagnosis, and broad claims about model families. Most limitations are directly supported by the implementation audit and are independent of experimental outcomes. The main revision need is editorial and epistemic: the draft repeatedly mixes enduring scope limitations, unresolved experimental specifications, correctable implementation defects, and instructions for the future experiment. Those categories have different consequences and should not be presented as though they were all observed threats in an executed study.

The section is not ready for final submission while the experimental protocol remains unverified. It is suitable as a pre-experiment draft if the explicit verification markers remain. Before results are reported, the owning author should resolve the blocking items below and rewrite each affected passage in the past tense around the protocol that was actually executed.

## Blocking revisions before results or submission

1. **Do not imply that the current repository defects affected experimental outcomes unless run artifacts show that they did.** The low-confidence terminal-message issue (current line 25), duplicate-ID behavior (line 35), permissive judge validation (line 37), unwired `db_on` and `crop_dict_on` fields, and the checked-in launcher defects are known properties of code paths, but the repository does not establish that these paths defined the reported runs. Each issue requires one of two treatments: fix it before running and remove it as a limitation of the study, or audit the executed outputs and report the resulting protocol deviation precisely. Phrases such as “may be appended,” “can collapse,” and “can lead to” currently stop between these two states and risk turning implementation bugs into speculative empirical claims.

2. **Add a condition-validity limitation or resolve the condition wiring before the section is finalized.** The most consequential known threat is currently absent. The repository defines seven named RAG configurations plus a separate direct-generation path, not a verified nine-condition matrix; `MainAgent` does not apply the declared base-collection or crop-dictionary flags; and the checked-in wrapper neither passes its ablation ID nor parses its `base` value as true. These facts do not prove that an external launcher was wrong, but they mean that condition labels alone cannot establish treatment assignment. The section should state, conditionally, that causal interpretation depends on verified launch manifests binding the agent switches to `--use_base_collection`, query-enrichment controls, `--no-rag`, runtime freshness, and unique output paths. If those manifests are supplied, retain only the residual limitation that prompt-controlled capabilities measure access rather than guaranteed per-item invocation.

3. **Replace unresolved model prose with the executed configuration once known.** Line 7 is accurate as a repository audit, but “the repository does not currently establish a Qwen-3 subject-model run” is not an enduring model-scope limitation. It duplicates Experimental Setup and will age badly. The final limitation should name the exact answer, controller, enrichment, extraction, and judge assignments used, then restrict generalization to those checkpoints, revisions, serving modes, and decoding settings. Do not characterize the paper as a Qwen-3 study until the subject-model role is supported; current evidence establishes Qwen3-32B only as a historical judge candidate.

4. **Resolve cohort construction before presenting paired comparisons.** The benchmark facts in line 35 are correct, but the effects should be stated exactly. `Inference/split.py` necessarily overwrites one row from each duplicate-ID pair when it constructs an ID-keyed mapping. Resume logic can skip an unprocessed member of a duplicate pair after the same identifier has been recorded. The splitter also excludes incomplete responses, which can create condition-specific cohorts. Assign collision-free row IDs and freeze a common cohort before inference/evaluation. If this is done, the duplicate IDs cease to be a study limitation and belong only in the data-preparation protocol; if legacy runs are used, report the audited number and identity of affected records rather than a hypothetical risk.

5. **Specify the analysis implied by shared runtime memory.** Line 31 correctly identifies cross-item dependence, but “treat the run ... as the unit of analysis” is incomplete unless there are multiple independent runs. A single stateful run does not support uncertainty estimation across run units. The revision should state the actual design: per-record isolation, a frozen replay/cache, or multiple independently initialized runs with an analysis that accounts for run-level clustering and order. Preserve dispatch and completion order and ingestion traces in any stateful design.

6. **Do not leave corpus provenance and judge validity as generic verification lists in the final paper.** Lines 13 and 37 contain essential unresolved protocol elements: the curated snapshot and source inventory, crop dictionary, embedding revisions, final judge, invalid-output policy, and repeated-judgment or human-validation procedure. These are prerequisites for interpreting results, not merely optional reproducibility details. Once resolved, move exact identities and policies to Experimental Setup and keep only the residual limitations: dependence on corpus coverage and selection, mixed date provenance, judge-mediated construct validity, and finite stability/validation evidence.

## Required content revisions

### Scope and external validity

- Line 5 is well scoped and independent of results. Retain the distinction between benchmark response generation and field or laboratory diagnosis. The phrase “broad mixture” is subjective; “includes identification, management, and gardening-guidance tasks” says the supported fact without implying breadth beyond the benchmark audit.
- The claim that the source-selection policy is tailored to “U.S.-oriented institutional sources” is only partly established. The web domain maps and state/hardiness-zone mechanism are U.S.-oriented, but the actual curated source inventory is unresolved. Attribute the statement specifically to the metadata and web-domain policy unless the completed corpus manifest verifies the base collection's geographic composition.
- Line 9 is a legitimate architecture-specific external-validity limitation. It can be shortened because the examples of sparse retrieval, learned reranking, end-to-end policies, and other runtimes are illustrative rather than evidence about observed behavior. State that conclusions apply to the implemented dense-retrieval and prompt-directed interfaces; avoid the speculative phrase “may not exhibit the same behavior.”

### Corpus and metadata dependence

- Line 13 appropriately identifies coverage and temporal-currency dependence. “Licensing” is not connected to a stated validity consequence and the repository does not establish the license status of the executed corpus. Remove it here or discuss it separately only after the source inventory is known.
- Make the LLM qualification gate's limitation explicit: corpus inclusion depends on an unvalidated model classification and the fixed rule that excludes `msc`. This is known independently of results. The current text names the gate but does not explain the selection-validity consequence or whether any human audit is planned. Do not claim that the gate introduced errors without an audit.
- Line 15 is one of the strongest passages. It accurately limits hardiness zone to a winter-temperature proxy and identifies omitted agronomic and jurisdictional variables without asserting observed failures. Retain it. Clarify that the state-modal fallback is used both for state-only inputs and unmatched counties, consistent with Methodology.
- The mixed provenance of `month_year` is correctly described. Use the same terms as Methodology: source date, provider-reported age or month-year, and acquisition month. The current phrase “month in which an undated page was acquired” is accurate but should not imply that all missing dates are known to be undated rather than absent from provider fields.
- Line 17 is factually grounded. Replace “controller following an allowlist instruction” with “enrichment model following an allowlist instruction” because query enrichment is a separate call that uses the controller endpoint, not a tool choice within the evidence-control trajectory. The character-subsequence validator blocks deletion, substitution, and reordering but does not prove token-level allowlist compliance or semantic appropriateness; the present consequence is stated correctly.

### Control-flow and measurement validity

- Line 21 correctly characterizes confidence as an uncalibrated routing heuristic. Use “score consistency” rather than “agreement among retrieval scores” to avoid anthropomorphic or evidential language. Also add the known instability that confidence performs a second retrieval whose model-supplied query, metadata, and `k` can differ from the initial retrieval and whose runtime collection may change between calls. This directly limits any interpretation that the score evaluates the evidence first returned to the agent.
- Line 23 is supported and belongs in the section. Distinguish tool availability, invocation, and correct ordered compliance. The phrase “causal interpretation of an ablation” is too broad because some candidate rows change bundles of mechanisms; say that component-level attribution requires both a contrast that isolates that component and manipulation checks demonstrating the effective tool calls and arguments.
- Line 25 accurately describes the logging gap and should remain, but it largely repeats Experimental Setup. Condense it around the validity consequence: current JSONL fields cannot establish treatment compliance or reconstruct evidence exposure. Keep the requested trace fields in Experimental Setup rather than repeating the complete inventory here.
- Treat the low-confidence terminal-message behavior as a blocking implementation audit, not a durable limitation. If fixed before all study runs, remove it. If not fixed, quantify affected records from traces and state the actual context-contamination rule and handling.

### Reproducibility and dependence

- Lines 29 and 31 are known independently of outcomes and appropriately scoped. They do not claim that external search variation caused a measured difference. Keep the core statements about mutable search results and shared runtime state.
- Replace “are needed to reproduce” with the actual protocol once selected. A versioned cache and complete live-search artifacts are alternatives with different guarantees: a cache supports replay of provider responses, while retained artifacts document but do not necessarily recreate changed or unavailable pages. Do not imply that timestamps and hashes alone make live acquisition reproducible.
- Explain that location-aware filtering changes the query itself, including site restrictions and suffix exclusions, so the filtered/unfiltered contrast bundles source restriction with query-string changes. This is a construct-validity limitation even under a frozen response protocol.
- The sentence “identical benchmark order alone does not guarantee identical runtime state” is correct because concurrent completion and ingestion interleave. Preserve it. Avoid claiming conventional item independence in any inferential statistics unless the analysis accounts for this shared state.

### Benchmark and evaluation validity

- Separate fixable cohort defects from residual benchmark limitations. After collision-free IDs and a frozen cohort are implemented, retain limitations that MIRAGE covers a finite set of seven categories, one benchmark distribution, one to three images, and the available geographic metadata. The current section discusses cohort integrity but says little about benchmark coverage beyond the opening paragraph.
- Line 37 correctly limits the model judge to rubric-mediated agreement with the provided expert response rather than direct field validation. It should also note that each record provides a single expert answer, so the rubric may penalize other valid recommendations or phrasings; this claim is warranted by the benchmark structure, but phrase it as a measurement limitation rather than asserting that such penalties occurred.
- The identification and management metrics have different scales and constructs. Identification combines a binary entity score with a 0--4 reasoning score, while management uses four 0--4 dimensions and a weighted composite. This limits direct comparison across task groups and should be stated if the paper later presents an overall system claim or pooled score.
- The current judge scripts' permissive validation and row removal are protocol defects. Correct them before evaluation where possible. If historical outputs are retained, audit invalid and dropped judgments per condition and report them; do not merely state that exhausted retries “can” remove records.
- Human validation is not automatically mandatory, but the paper must disclose whether it was performed. If none was performed, state that judge validity was not externally calibrated rather than leaving `[DETAIL REQUIRES VERIFICATION]` or implying an undocumented procedure.

## Redundancy and organization

The section repeats many details already stated in Methodology and Experimental Setup: exact missing model fields, corpus-manifest contents, trace-field inventories, duplicate counts, invalid-judge mechanics, and required run artifacts. Limitations should cite or briefly recall the mechanism and focus on the inferential consequence. A cleaner final organization would preserve the current five themes but use one paragraph per threat: scope/model generalization; corpus selection and metadata proxies; controller and confidence construct validity; online/shared-state reproducibility; benchmark and judge validity.

The imperative language (“requires,” “must,” “should retain,” “must either”) makes parts of the section read like an experiment checklist. Before submission, replace it with a description of the executed mitigation and the remaining limitation. Until execution details exist, imperative language is appropriate for this internal draft, but it should not survive into the camera-ready prose.

## Optional improvements

- Define “evidence-bearing output” once and use it consistently with the Methodology distinction between successful context use and the canonical no-evidence message.
- Use *query enrichment*, *confidence evaluation*, *progressive metadata retrieval*, *curated base collection*, and *runtime collection* exactly as defined in `paper/notes/terminology.md`.
- Avoid repeating “not a calibrated probability” in both Introduction and Limitations at length; retain the formal explanation in Methodology and one concise consequence here.
- If space is tight, remove examples of alternative retrieval architectures before cutting the hardiness-zone, mutable-web, shared-runtime, or judge-validity paragraphs; those four threats are more specific to the study and more informative to readers.

## Revision decision

**Major revision required.** No unsupported experimental result is currently asserted, and the core limitations are grounded in repository evidence. The blocking concern is that several known code defects and missing run specifications are expressed as hypothetical threats. Final prose must identify which defects were corrected before execution, which affected actual runs, and what residual limitations remain after mitigation.
